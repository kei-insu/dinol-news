### 구분 판정

| 구분 | 기준 |
|---|---|
| `분석` | 코드·파일을 바꾸지 않고 확인·측정·감사만 한 작업. **커밋이 생기면 `개발`, 안 생기면 `분석`** |
| `변환` | 기존 데이터를 옮기거나 값을 채우는 파이프라인 작업 |
| `배포` | 브리핑 발행·릴리스 등 배포 검증까지 끝난 작업 |
| `문서` | `docs/` 문서 갱신 |

### 기록 시점

| 시점 | 결과 |
|---|---|
| 작업 완료 · `git push` 성공 · 배포 검증 | `완료` |
| 시도했으나 실패 | `실패` |
| 되돌림 | `롤백` |
| 논의 후 보류 | `보류` |

> **끝나지 않은 일은 작업 일지에 쓰지 않는다.** 착수 전 과제는 백로그 DB로 보낸다. `대기`는 백로그 DB가 없던 시기의 잔여 옵션이다.

### 필드 작성 규칙

- `커밋` = 이번 작업 해시 / `이전커밋` = 되돌아갈 해시. **본문에 쓰지 않고 각 필드에 넣는다.**
- 배포 행의 `이전커밋`이 비어 있으면 기입하지 말고 먼저 확인한다.
- `날짜`는 시간까지 넣는다(KST `+09:00`). 같은 날 여러 건의 순서를 복원하기 위함이다.
- `작업명` 40자 이내. 날짜·버전·프로젝트를 제목에 넣지 않는다.
- `내용`은 결론 2~3줄, 수치로 쓴다. 중간 진행 상황은 기록하지 않는다.
- **실패·롤백도 기록한다.** 실패 기록이 없으면 같은 시도를 반복하게 된다.

### 작성 원칙
- **무엇을 왜 했는지**를 남긴다. 파일명 나열이 아니라 판단 근거와 수치를 적는다.
- 발견한 결함·수치(예: "EN 카드 8장 결함", "전수 검증 209장 0건")를 함께 적는다.
- 세션 종료 전 미기록 항목이 없는지 확인한다.
